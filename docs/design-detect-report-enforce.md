# Design Doc: 検出・報告・強制の分離（scan アーキテクチャ再設計）

- ステータス: ドラフト v3（第1回・第2回反証レビュー反映済み。
  v3 で §6.8 カテゴリ範囲選択を追加）
- 作成日: 2026-08-06 / v2 改訂: 2026-08-06 / v3 改訂: 2026-08-06
- 関連: PR #166（氏名検出の既定カバレッジ拡大。本設計の先行実装にあたるが、
  検出オプトインの枠組み自体は現状のまま）
- レビュー履歴: §12 参照。v1 に対する反証レビューで 12 件の反例が成立し、
  移行順序・互換性・性能前提を中心に改訂した。

## 1. 要約

jp-pii-detect の「何を検出するか」を設定から切り離し、常に全ルールで検出する。
そのうえで「どう見せるか（報告）」と「何でコミット・CI を失敗させるか（強制）」を
独立した層として再設計する。誤検出の抑制は、検出範囲を狭めるのではなく、
文脈による確信度の校正と、低確信度候補の集約表示で行う。
利用者が触る概念は「検出モード」ではなく「失敗させる閾値（--fail-on）」だけにする。

## 2. 用語

本文書で使う用語を先に定義する。

- **PII**（Personally Identifiable Information、個人情報）:
  氏名・電話番号・マイナンバー等、個人を識別しうる情報。
- **適合率（precision）/ 再現率（recall）**:
  適合率は「検出したもののうち本物の割合」、再現率は「本物のうち検出できた割合」。
- **確信度（confidence）**: 各検出に付く low / medium / high の3段階。
  「人間の読み手がどの程度の確度で PII と同意するか」の校正値として扱う。
- **オプトイン（opt-in）**: 既定では無効で、フラグや設定で明示的に有効化する方式。
  現状の `--high-recall` / `--name-roster` がこれにあたる。
- **強制（enforcement）**: 検出結果に基づいて終了コードを非 0 にし、
  pre-commit フックや CI のジョブを失敗させること。
- **ベースライン（baseline）**: 既存の検出を記録しておき、以降の走査では
  新規追加分だけを報告する既存機構（`--baseline` / `--update-baseline`）。
- **ドッグフーディング（dogfooding）**: このリポジトリ自身を自分のバイナリで
  走査する CI ゲート。現在は「検出 0 件」を要求している。

## 3. 背景と問題

### 3.1 起きたこと

利用者が `担当: 山田太郎` を含むファイルを既定設定で走査し、氏名が検出されなかった。
原因は欠陥ではなく仕様で、担当ラベルの氏名検出が高再現率オプトインに
割り当てられていたためだった。利用者はこれを「フラグが足りない」ではなく
「検知できなかった」と受け取った。

この個別事件そのものは PR #166 が、検出オプトインの枠組みを変えずに
（担当ラベルを既定ルール `person-name-role-label` へ分離して）解決済みである。
本設計が対象にするのはこの一件ではなく、**同型の事件が構造的に再発すること**である。
現状の枠組みでは、新しい検出能力（名簿判定・Markdown テーブル・クロスライン等）を
追加するたびに「既定に入れると誤検出が増えるためオプトイン行き」という判断が
繰り返され、検出能力と初見の利用者が実際に受け取る検出結果の乖離が拡大し続ける。
PR #166 の名簿判定（`--name-roster`）がさっそく 3 つ目のオプトイン軸に
なりかけたことが、その実例である。

### 3.2 実測データ

数値は 2026-08-05〜06 に、このリポジトリと合成ファイルで計測した。
v1 に記載した数値のうち 2 点は反証レビューで誤りが確認されたため修正済み（§12）。

- 現実的な氏名ラベル 14 種を並べたファイルに対し、PR #166 以前の既定で
  検出できたのは `氏名:` / `名前:` / `顧客名:` の 3 種のみ。`担当:` / `宛名:` /
  敬称付き・名簿形式・Markdown テーブルはすべて 0 件だった。
- このリポジトリを `--high-recall` で走査した検出件数は、設定条件で大きく変わる。
  allowlist（自リポジトリの `.jp-pii.toml`。テストフィクスチャ・docs 等を除外）を
  読まない条件では 631 件、実運用の設定ファイルを読む条件では 145 件
  （PR #166 適用後は 158 件）。両条件とも `internal/dict/towns.txt`
  （町字名辞書）への `person-name-high-recall` の誤検出 124 件を含む
  （`一乗寺払殿町` の「殿」等が敬称アンカーに一致するため。この辞書は
  allowlist の除外対象ではない）。
- 誤検出しやすい負例 10 行（`担当: 営業部` / `担当者: 未定` 等）に対し、
  担当ラベル側の検出（姓名辞書ゲートあり）は 0 件だった。

つまり「既定は取りこぼしが多すぎる」と「全部有効は誤検出が多すぎる」が
同時に成り立っており、どちらの極も初見の利用者を失望させる。

### 3.3 根本の問題

利用者の頭の中では、PII かどうかは**データの属性**であって走査設定の属性ではない。
`--high-recall` というフラグは、正規表現と辞書という実装技術の
適合率・再現率トレードオフを、そのまま利用者の意思決定として露出している。
利用者は自分が「高再現率が欲しいか」を知らない。知っているのは
「顧客データの棚卸しをしている」か「コードをコミットしようとしている」かである。

さらに、検出・表示・強制の 3 つの判断が `min_confidence` と検出オプトインの
2 つのつまみに混在しているため、再現率を上げる改善が常に
「pre-commit を煩くする変更」として現れ、改善が構造的に進めにくい。

## 4. 利用者の期待の整理

### 4.1 無条件の期待（場面によらない）

1. **見ればわかる PII は、設定なしで全部見つかる。** 人間が一目で氏名と
   わかるものをツールが見つけないのは、利用者には検出器の欠陥に映る。
2. **見ればわかる非 PII は報告されない。** 「現行仕様」を氏名と報告した
   時点で、以後の全検出への信頼が毀損される。
3. **判断の理由が見える**（`--explain` で現状も提供済み）。
4. **一度下した判断は繰り返し聞かれない**（ignore マーカー・allowlist・
   baseline で現状も提供済み）。
5. **ファイルを渡せば読める**（BOM・Shift_JIS・UTF-16・JSON エスケープ対応済み）。
6. **速い**（リポジトリ全体で数十秒以内）。

期待 1 と 2 は利用者の中では単一の期待の両面である。人間の読み手は
両者を日常的に両立しているため、利用者の頭の中に適合率と再現率の
トレードオフは存在しない。

### 4.2 状況で反転する期待

7. **コミット時**: 本物の事故だけ止めてほしい。誤ブロックは `--no-verify`
   常用、すなわちツール外しに直結する。
8. **監査・棚卸し時**: ノイズは自分で読むから漏れなく列挙してほしい。
9. **CI 導入時**: 既存分は責めず、新しく入る分だけ守ってほしい。
10. **組織導入者**: チームに外されないこと自体が要求。ノイズ管理は
    利用者の我慢ではなくツールの仕事。

期待 7 と 8 で変わっているのは「検出してほしい範囲」ではなく、
「検出結果にどう振る舞ってほしいか」である。ここが本設計の軸になる。

## 5. 設計原則

- **原則 A（検出の一本化）**: 全ルールを常時実行する。検出範囲を変える
  設定を持たない。期待 1 は無条件なので、「その名簿を検出しない設定だった」
  という状態を存在させない。
  **適用範囲の明確化（v2）**: 原則 A が解くのは「実装済みルールが設定次第で
  適用されない」問題であって、語彙・辞書のカバレッジ問題ではない。
  `申込者: 加藤八郎` のようにラベルが語彙外のケースは、全ルールを有効にしても
  0 件のままである（反証レビューで実測）。語彙カバレッジは原則 A とは独立の
  継続的なルール改善であり、原則 A の価値は「その改善が入ったとき、
  オプトインの壁なしに全利用者へ届く」ことにある。
- **原則 B（文脈による確信度校正）**: 同じ文字列でも、ファイルの種類と
  場所で確信度を変える。`data/customers.csv` の氏名列は高く、`.go` の
  コメント中は低く、辞書様ファイル（後述）では候補どまり。期待 2 を、
  検出を削らずに満たす手段。
- **原則 C（報告は集約、強制は一軸）**: 低確信度候補が同一ファイルに
  多数あるときは集約して 1 行にする。終了コードは `--fail-on` 閾値だけが
  決める。「検出される」「表示で埋もれない」「コミットが止まる」を
  独立に制御する。
- **原則 D（強制は新規のみ）**: pre-commit / CI の強制は差分と baseline を
  前提にし、既存資産を責めない。
- **原則 E（検出境界の明文化）**: 原理的・実装的に見つけられないものを
  docs で公開する。対象は「辞書外の無ラベル氏名」「ファイルに 1 件だけの
  裸の氏名」に加え、**「辞書内の氏名 + ラベル語彙外のラベル」**
  （反証レビューで最大級の取りこぼしクラスと確認された）を含む。

## 6. 具体仕様

### 6.1 検出パイプライン（原則 A）

- 既定無効化の枠組み（`config.applyOptInRuleDefaults` による
  `rule.HighRecallRuleIDs()` / `rule.NameRosterRuleIDs()` の自動 disable）を
  廃止し、`detect.New` は常に全ルールを構築する。関数自体は評価系
  （`internal/eval` / `internal/corpusv2`）が参照しているため、削除ではなく
  「確信度階層の宣言」として残す。
- 旧オプトインのルール群は「検出しない」から「確信度を下げて検出する」に
  意味を変える。例: 敬称アンカーの検出は既定 low（現行の high-recall 有効時
  medium から降格）とし、6.2 の文脈校正で昇格しうる。
- **性能（v2 で全面改訂）**: v1 の「+20% 以内」は反証レビューの実測で
  達成不能と確認された。全ルール常時実行の実測（このリポジトリ、
  最適化なしの素朴な実装）: 純 ASCII 行 +98%、CJK 1 行（町字名）+2219%、
  フルスキャン wall +420% / CPU +200%。25MB の日本語テキスト木では
  wall 0.91s → 5.57s。名簿統計の常時実行だけでも wall +99%。
  したがって原則 A の実装には**プリフィルタ強化が前提条件**になる:
  敬称アンカー等の高コスト正規表現へのゲート追加（`internal/detect/pattern_gate.go`
  の既存機構の拡張）、名簿統計のサンプリング化（全行でなく先頭 N 行 +
  一様サンプルで割合を推定）等。受け入れ条件は「最適化後に実測して設定する」
  とし、目安として既定フルスキャンの wall +50% 以内を目標に置くが、
  これは未検証の目標値である（推測）。達成できない場合は原則 A 自体を
  再検討する（§9-6）。

### 6.2 文脈による確信度校正（原則 B）

`internal/detect/path_profile.go`（テスト経路の降格）と PR #166 の名簿判定
（ファイル統計での判定）を一般化し、「ファイル種別推定」を導入する。

- **データ様**（`.csv` / `.tsv` / `.sql` / 列構造を持つ `.md` テーブル /
  名簿統計を満たすテキスト）: 氏名・番号系の確信度を 1 段昇格しうる。
  ただし**名簿統計単独では high へ昇格させない**。high への昇格は、
  同一ファイル内に他カテゴリの検証済み PII（電話番号・郵便番号等）が
  共起する場合に限る（既存の cooccurrence boost と同じ思想）。
  これは「実在の町字名 5 行のファイルが名簿判定を通過して high に達し、
  pre-commit を誤ブロックする」という反証シナリオ（§12 S5）の遮断策。
- **辞書様**: 短い CJK 行が大量（目安: 数千行以上）に並び、姓名辞書分割の
  成立率が低く、他カテゴリの PII が共起しないファイル。**氏名系・住所系の
  検出**を候補（low）に降格する（v1 の「氏名系のみ」では
  `internal/dict/towns.txt` に `jp-address-high-recall` の medium が
  4 件残ることが反証レビューで確認されたため、住所系を対象に加えた）。
  実測の分離度: towns.txt は非空 95,007 行中 184 行（約 0.194%）しか
  姓名分割が成立せず、本物の名簿（過半が成立）と統計的に分離できる。
  **既知の限界**: この分離は行数の少ないファイルでは効かない。実在の
  町字名を 5 行だけ並べたファイルは統計上、本物の名簿と区別できない
  （反証レビューで medium 検出を確認）。小さいファイルの辞書様判定は
  行わず、medium 止まり（high 昇格なし）+ 集約対象とすることで
  影響を強制層に波及させない。
- **コード様**（既存の `sourceExtensions`）: 現行どおりラベル文脈で判定し、
  コメント中の裸の CJK 列からの氏名昇格はしない。
- **文書様**（`.md` / `.txt` のうち上記に該当しないもの）: 補正なし（基準値）。

誤推定時の安全側は「補正しない」とする。種別推定に確信が持てない場合は
基準値のままにし、降格も昇格もしない。

### 6.3 報告（原則 C）

- **端末向け text 出力**: high / medium は現行どおり 1 件 1 行。low は
  **同一ファイル×同一ルールで 5 件以上のときのみ**
  「`internal/dict/towns.txt`: 氏名候補 184 件（低確信度）」の形に集約し、
  `--expand-low`（新設）で展開できるようにする。5 件未満は個別表示する。
  この閾値は「`.txt` の議事録に書かれた 1 件の敬称付き氏名が、集約に
  吸われて実質見えなくなる」という反証シナリオ（§12 S12）の遮断策。
  閾値 5 は仮置きであり、ステップ 1 のドッグフーディングで調整する。
- **json / sarif 出力**: 機械可読形式は原則全件を含める（confidence
  フィールドで消費側が絞る）。ただし **GitHub code scanning は 1 run
  あたり 5,000 件までしか取り込まない**（反証レビューで公式ドキュメントを
  確認。超過分は黙って切り捨てられる）ため、sarif 出力には確信度下限
  オプションを設け、GitHub 連携のドキュメントで明示する。
- **github 出力**: PR 注釈のスパム化を避けるため、注釈は `--fail-on` 閾値
  以上のみとし、それ未満はサマリ 1 行にまとめる。
- **終了判定との関係（v2 で明確化）**: 集約表示された low 候補は
  **終了判定に影響しない**。終了コードは 6.4 の `--fail-on` 閾値のみが決める。

### 6.4 強制（原則 C・D）

- 終了コード契約（0=なし / 1=検出 / 2=エラー）は維持する。
  「1 を返す条件」だけを `--fail-on` 一軸に整理する。
- **`min_confidence` との互換橋渡し（v2 で追加）**: 現行実装では
  `min_confidence` は表示閾値であると同時に、`--fail-on` 未指定時の
  事実上の終了判定閾値でもある（`cmd/jp-pii-detect/main.go` の `shouldFail`
  は報告対象の有無を見るため。`docs/cli.md` も「報告対象の検出が 1 件でも
  あれば終了コード 1」と公開契約している）。したがって
  **`min_confidence` が設定されていて `--fail-on` が未指定の場合、
  `--fail-on` は `min_confidence` の値を引き継ぐ**。これにより
  `min_confidence = "high"` の利用者（現行 exit 0）が新設計で exit 1 に
  反転する事故、および `min_confidence = "low"` の利用者（現行 exit 1）が
  黙って exit 0 になる事故（いずれも反証レビューで再現）を防ぐ。
- 呼び出し文脈別の既定値:
  - **対話実行**（`scan <path>`）: `--fail-on medium`（現状の既定と同じ挙動）。
  - **pre-commit フック**（`--staged`）: **当面 `--fail-on medium` を維持する**
    （v1 の high 推奨から変更）。反証レビューで、high 限定では
    `氏名,郵便番号,生年月日` の顧客 CSV 追加が終了コード 0 で素通りする
    ことが実証された（これらの中核 PII は現行ルールで medium 止まりのため）。
    high への引き上げは、6.2 の文脈昇格（データ様ファイルでの medium→high）が
    先に本番投入され、「hook を high にしても本物のデータファイル追加は
    high で捕まる」ことが実測で確認できた後にのみ行う（§7 の順序制約）。
  - **CI 差分走査**（`--diff`）: `--fail-on medium` + baseline。

### 6.5 CLI・設定の互換マッピング

| 現行 | 新設計での扱い |
|---|---|
| `--high-recall` | 廃止予定（deprecated）。指定時は警告のみで挙動に影響しない（検出は常に全ルールのため） |
| `--name-roster` | 同上 |
| `[rules] high_recall` / `name_roster`（TOML キー） | **フィールドを維持し、受理して無視する**（v2 で追加）。フィールドを削除すると未知キー警告（`internal/config/config.go` の warnings 機構）が既存設定ファイルの利用者に毎コミット出るため、削除はしない |
| `min_confidence` | キー維持。「隠す」から「5 件以上は集約に畳む」へ読み替え。かつ `--fail-on` 未指定時は終了判定閾値として引き継ぐ（6.4） |
| `--fail-on` | 強制の唯一の軸として維持・昇格 |
| `[rules] disabled` | 維持（個別ルールの完全無効化は引き続き可能） |
| baseline / ignore マーカー / allowlist | 変更なし。baseline の fingerprint は確信度を含まない（`internal/baseline/baseline.go`）ため、6.2 の確信度校正で既存 baseline は無効化されない（反証レビューで確認） |

### 6.6 ドッグフーディング CI の契約変更

「検出 0 件」を「`--fail-on` 閾値（medium）以上が 0 件」に変更する。
ただし契約変更だけでは足りないことが反証レビューで確認されている:
原則 A の最小実装でこのリポジトリを実運用設定付きで走査すると
**158 件（medium 153 / high 5）**が出る。内訳と対処:

- `person-name-high-recall` 148 件（大半が towns.txt）: 6.2 の辞書様降格
  （low 化）+ 敬称アンカーの基準確信度 low 化で解消する設計。
- `jp-address-high-recall` の towns.txt 内 medium 4 件: 6.2 の降格対象を
  住所系に広げたことで解消する設計。
- `internal/corpusv2/corpusv2_test.go` の Base High 5 件（`渋谷区神南1-2-3` 等）:
  確信度校正では解消しない（Base High は降格対象外）。リポジトリ側の
  対処（ignore マーカーまたは allowlist 追加）が必要。

### 6.7 評価体系の再構成

現在の `docs/accuracy.json` は low / medium / high-recall という
「検出範囲別」プロファイルで、混在コーパス上の単一 F1 を指標にしている。
この構造では再現率の改善が常に適合率の悪化として現れる。

- 私設コーパスの各ケースに**文脈タグ**（データ様 / コード様 / 文書様 /
  辞書様）を付与し、指標を「コード文脈の適合率」「データ文脈の再現率」の
  ように文脈別に分ける。
- 目標値も文脈別に設定する（例: コード文脈の適合率はデータ文脈より
  高く要求する）。具体値は移行の最終ステップで実測に基づいて決める。
- **段階の分離（v2 で明確化）**: 全面再構成は最終ステップに置くが、
  評価系への影響はステップ 1 の時点で不可避に発生する（§7 参照）。
  「評価コストをすべて最終ステップへ先送りできる」という v1 の記述は
  誤りだった。

### 6.8 カテゴリによる範囲選択（`--only`）

利用者の作業単位（棚卸し・調査・監査）は「人名」「電話番号」といった PII の
カテゴリで語られる。ルール ID の内部分類（person-name 系だけで 6 ID）を
知らなくても範囲を絞れるよう、カテゴリ単位の選択を追加する。

- **CLI**: `--only <category>[,<category>...]`（カンマ区切り）。繰り返し
  指定した場合は既存の CLI 規約どおり最後の指定が勝つ（`reorderArgs` が
  明文化している規約に合わせ、`--only` だけを累積の例外にしない）。
  無指定は全カテゴリ（6.1 の常時全検出と同じ）。未知のカテゴリ名は
  エラーにし、有効なカテゴリ一覧を表示する。`--only` 指定時は summary 行に
  有効カテゴリを常に表示する（範囲を絞ったまま忘れる事故の可視化）。`scan` の位置引数はパスに
  使用済みのため、選択は必ずフラグで行う（`scan 人名 .` のような位置引数
  方式は、同名ディレクトリとの衝突と `parseFlagArgs` の並べ替えロジックとの
  干渉があるため採らない）。
- **設定ファイル**: `[rules] only = ["phone", ...]` を CLI と同義のキーとして
  用意する（CI 用）。`[rules] disabled` は選択後にも適用される
  （カテゴリで選んだ集合から、さらに個別ルールを disabled で除ける）。
  `disabled`（denylist）と `only`（allowlist）は将来のルールに対して
  非対称であることに注意: `disabled` では新規追加ルールが常に有効側に
  入るのに対し、`only` では新規ルールが黙って対象外になりうる
  （第2回反証レビューで指摘）。緩和は前述の summary 表示に加え、
  継続運用の CI には `only` ではなく `disabled` を推奨する注記を
  docs に置く。
- **意味論（部分集合不変条件）**: カテゴリ指定は**報告層のフィルタ**として
  定義する。検出は 6.1 のとおり常に全ルールで行い、報告・強制の対象を
  指定カテゴリの findings に絞る。これにより「カテゴリ指定時の結果は、
  無指定時の結果から当該カテゴリの findings を抜き出したものと 1 件も
  違わない」ことが保証される（カテゴリ指定を感度の選択にしない、という
  本設計の要請そのもの）。
  報告層フィルタとして定義しなければならない理由は、検出層でルールを
  止めると結果が変わるルール間相互作用が実在するため:
  1. **重複解決はカテゴリをまたぐ**: 例えば `連絡先: 山田太郎@kaisha.co.jp`
     では email-address-eai と person-name-role-label が同一スパンで競合し、
     確信度の高い email 側が残る（high vs medium。`resolveOverlaps` の
     第 1 キーは確信度で、スパン長は下位のタイブレーク。
     `internal/detect/detect_test.go` の TestInternationalEmailHighRecall で
     固定済みの挙動）。検出層で email を止めると name 側の finding が
     「出現」し、無指定時に存在しなかった結果が生まれて部分集合不変条件が
     壊れる。
  2. **共起ブーストはカテゴリをまたぐ**: `cooccurrence_boost`（opt-in）は
     電話番号等のアンカーで氏名系の確信度を昇格させる。検出層でアンカーの
     カテゴリを止めると、氏名の確信度が無指定時と変わる。
  3. **数字系ルール同士も同一スパンで競合する**（第2回反証レビューで実測）:
     jp-my-number と jp-drivers-license / jp-phone-number、jp-birthdate と
     jp-health-insurance の競合が実リポジトリの走査で確認されている。
     この列挙は網羅ではなく、だからこそ意味論を報告層フィルタで定義する
     （個別の相互作用の発見に依存しない）。
  部分集合不変条件を守っても、カテゴリ指定の走査は「他カテゴリのルールが
  同一スパンで勝った値」を報告しない点は仕様として明記する（実測例:
  `保険者番号 生年月日: 19850102` を含む入力に対し `--only birthdate` は
  0 件・exit 0。全カテゴリ走査では jp-health-insurance が同スパンで勝つ
  ため）。監査用途では意外性があるため、「他カテゴリとして検出された
  同一スパンが N 件ある」旨のヒントを summary に出す案を §10 に積む。
  同じ理由で、確信度校正（6.2）が入ると同一スパンの勝者が変わり、
  カテゴリ帰属が移行ステップ間で移動しうる。`--only` の監査結果を
  ステップをまたいで比較する場合はこの点に注意が要る。
  検出層でのルールスキップは、**findings（報告・強制・baseline に使う集合）が
  変わらないことを保証できる場合に限った最適化**として許す。第2回反証
  レビューを受けて、この最適化の境界を次のとおり限定する:
  - スキップするのは**ルールの実行**であって、Detector が持つルール集合
    ではない。`rules` サブコマンドの一覧と SARIF の `driver.rules` 列挙は
    常に全ルール基準で不変とする（`det.Rules()` は最適化の影響を受けない）。
  - `--explain-dropped` 指定時は検出層スキップを行わない。棄却候補の記録は
    ルール横断の共有予算（`maxDroppedCandidates` = 1000）を持ち、スキップで
    記録内容が変わることが実測されているため（診断モードは速度より
    完全性を優先する）。
  - 例: `--only phone` かつ `cooccurrence_boost` 無効時の氏名系ルールの
    スキップは、findings については 17 種の敵対的入力（全角数字・長音
    セパレータ・CSV/SQL/Markdown・氏名と番号の連結等）と実リポジトリ全体の
    差分比較で差分ゼロを確認済み（第2回反証レビュー）。上記 2 つの制約の
    下でのみ適用する。
  この最適化が効くのは `--only` を使う監査走査に限られ、6.1 の既定
  フルスキャン（カテゴリ無指定）の性能問題には効かない（実測: phone のみで
  走査時間は全ルール比 8% まで短縮する一方、無指定時は変化なし）。6.1 の
  プリフィルタ強化は引き続き別途必要である。
- **baseline との相互作用**（第2回反証レビューで全面改訂）: 通常の走査では
  フィルタは報告対象を減らすだけで fingerprint に影響しない。
  `--update-baseline` 併用時の危険は、v3 初稿が書いた「上書きによる既存
  エントリの消失」では**ない** — 現行実装は既存ファイルへ追記専用の
  `baseline.Merge` を使うため、消失はもともと起きない。実在する危険は逆で、
  現行の `--update-baseline` は表示フィルタ適用**前**の findings を記録する
  （`cmd/jp-pii-detect/main.go` の classifyFindings より手前で早期 return）。
  カテゴリフィルタを表示フィルタと同列に「適用しない」扱いにすると、
  `--only phone --update-baseline` が全カテゴリの検出を baseline に焼き込み、
  以後の全カテゴリ走査で氏名等の既存検出が黙って消える。
  仕様: カテゴリは表示の絞り込みではなく**走査範囲の宣言**として扱い、
  baseline 更新はカテゴリフィルタ**後**の findings に限定する
  （`min_confidence` 等の表示フィルタは従来どおり適用しない、という
  既存原則はカテゴリ以外について維持する）。選択外カテゴリの既存エントリの
  保持は `Merge` の追記専用の意味論で担保される。
- **rules サブコマンド**: 一覧にカテゴリ列を追加する。`only` が設定されて
  いる場合は選択外のルールに「対象外」タグを表示する。runRules の
  「scan が実際に使うルール集合と一致する」という既存の契約
  （`cmd/jp-pii-detect/main.go` の関数コメント）を、カテゴリ導入後も
  維持するため。

カテゴリ分類（v3 時点の草案。粒度は §10 で再検討）:

| カテゴリ | 含まれるルール |
|---|---|
| `name` | person-name / person-name-role-label / person-name-high-recall / person-name-structured / person-name-roster / person-name-romaji |
| `address` | jp-address / jp-address-high-recall / jp-postal-code |
| `phone` | jp-phone-number |

| `my-number` | jp-my-number / jp-juminhyo-code |
| `id-document` | jp-drivers-license / jp-passport / jp-residence-card / jp-pension-number / jp-health-insurance / jp-employment-insurance / jp-kaigo-insurance |

## 7. 移行計画

v1 から順序を変更した（反証レビュー §12 S1・S7 の反映）。
文脈確信度を強制変更より先に置き、各ステップの評価系コストを明記する。

1. **集約表示 + 常時検出 + カテゴリ範囲選択 + 評価系の追随（旧ステップ 1 拡張）**:
   検出フラグを deprecated 化し、既定で全検出 + low の集約表示にする。
   カテゴリ範囲選択（6.8）もこのステップに含める。
   `min_confidence` の橋渡し（6.4）により、既存の hook / CI の終了コードは
   変わらない。**このステップに含まれる評価系作業（v2 で追加）**:
   原則 A の最小実装だけで既存テストが 23 件落ちることが確認されている
   （`internal/config` 6 件、`internal/detect` 15 件、`internal/eval` 2 件
   ほか）。`internal/eval/profiles.go` のプロファイル定義変更、
   `docs/accuracy.json` の low / medium プロファイル再生成、README の
   バッジ・精度表の更新（medium プロファイルの数値がこの時点で動く）、
   ドッグフーディング契約の変更（6.6）と自リポジトリの allowlist 追加が
   必要になる。私設コーパスへのアクセスが必要なため、CI 側での再生成を
   前提にする。あわせて性能最適化（6.1 のプリフィルタ強化）をこの
   ステップの受け入れ条件とする。
2. **文脈確信度（旧ステップ 3 を前倒し）**: ファイル種別推定を導入し、
   敬称アンカー等の基準確信度を再配置する。データ様ファイルでの
   medium→high 昇格の適合率を実測する。
3. **強制の整理（旧ステップ 2 を後置）**: ステップ 2 の昇格が「本物の
   データファイル追加を high で捕まえる」ことを実測で確認できた場合に
   限り、pre-commit テンプレートの既定を `--fail-on high` に引き上げる。
   確認できない場合は medium のまま維持する（6.4）。
4. **評価体系の全面再構成**（6.7）: 文脈タグ別指標への組み替え。
   ステップ 1〜3 の観測結果が出てから着手する。

## 8. 却下した代替案

- **現状維持（検出オプトイン方式）**: 期待 1 の違反が構造的に残る。
  検出能力の改善のたびにオプトインが増え（PR #166 で 3 軸目が発生しかけた）、
  発見可能性が下がり続ける。
- **呼び出し文脈（TTY 判定等）で検出範囲を切り替える**（本設計の前身案）:
  `scan .` と `scan . | cat` で検出件数が変わる。同じ入力に対して結果が
  再現しないのは走査ツールとして最悪の性質であり、CI へのコピペで
  挙動が変わる事故も誘発する。検出は不変、変えるのは表示と強制のみ、
  という本設計の形に修正した。（反証レビューでもこの棄却理由に穴は
  見つからなかった。）
- **全ルールを既定 medium で有効化し、pre-commit も止める**: 実運用設定でも
  このリポジトリで 158 件（medium 以上）が出る実測から、コードリポジトリでの
  誤ブロックが多発し、ツール外し（期待 7・10 の違反）に直結する。

## 9. リスクと反証可能条件

この設計が間違っていた場合に、それをどう検知するかを先に決めておく。

1. **「提示で解決できる」仮説の反証**: 集約表示にしてもなお「候補が出る
   こと自体が煩わしい」という反応が支配的なら、原則 C の前提が崩れ、
   既定抑制（現状設計）が正しかったことになる。判定材料: ステップ 1
   リリース後のドッグフーディングと利用者フィードバック。
2. **集約が警告を殺すリスク**: 集約行を誰も開かず、その中に本物が埋もれる。
   緩和: 集約は low のみ・同一ファイル×ルール 5 件以上に限定し、
   少数の候補は常に個別表示する（6.3）。それでも「大量候補ファイルの中の
   本物 1 件」は原理的に埋もれる。このケースはデータ様昇格（6.2）が
   拾う設計だが、昇格の取りこぼしはこのリスクを直接悪化させる。
3. **ファイル種別推定の誤りによる降格事故**: 本物の顧客名簿を辞書様と
   誤判定すれば、検出はされるが候補に埋もれる。緩和: 辞書様判定は
   大きいファイル + 姓名分割成立率が低い場合に限定する。
   **既知の限界（v2 で拡充）**: (a) 小さい辞書様ファイル（町字名 5 行等）は
   本物の名簿と統計的に区別できず、medium で検出される（high 昇格と
   強制には波及させない）。(b) カタカナのみ・辞書外氏名主体の本物の名簿は
   成立率が低く出るため、名簿と認識されない。いずれも原則 E で明文化する。
4. **強制閾値と検出能力の不整合リスク**: 反証レビューで「hook を high に
   すると氏名・郵便番号・生年月日の CSV が素通りする」ことが実証された。
   v2 では hook 既定を medium に据え置き、high 化を文脈昇格の実測後に
   条件付きで行う順序に変更した（6.4、§7）。この順序でも、ステップ 2 の
   昇格適合率が低ければ high 化は永久に行えず、その場合は「hook は
   medium のまま + 誤検出は集約と ignore で運用」が定常状態になる。
   それを失敗と見なすかどうかは、hook の誤ブロック実測頻度で判断する。
5. **移行コストの過小評価**: v1 は評価系コストを最終ステップに先送り
   できると誤認していた（反証レビューで、原則 A の最小実装だけで
   テスト 23 件が落ち、accuracy.json の再生成がステップ 1 で必要になる
   ことが確認された）。v2 はステップ 1 にこのコストを計上した。それでも
   私設コーパス側の作業量は未見積りであり、ステップ 1 の着手前に
   コーパス管理者との見積り合わせが必要である。
6. **性能の壁**: プリフィルタ強化後も既定フルスキャンの劣化が
   目標（+50% 以内、暫定）に収まらない場合、原則 A は「全ルール常時」から
   「軽量ルール常時 + 重量ルールはファイル種別で選択実行」に後退させる。
   この後退は「検出結果がファイル内容に依存して変わる」ことを意味するが、
   「設定に依存して変わる」現状よりは期待 1 に近い。

## 10. 未解決の問題

- 集約表示の具体的な UI（展開の操作性、`--format github` のサマリ文面、
  集約閾値 5 件の妥当性）。
- ファイル種別推定の判定アルゴリズムの詳細と、その単体テスト戦略。
- baseline が監査モードの大量候補（数千件規模）を記録する際の
  ファイルサイズとマージ衝突の扱い。
- 敬称アンカー等、旧 high-recall ルールの基準確信度の再配置の具体値。
- 名簿統計のサンプリング化（6.1）の具体設計と、サンプリングによる
  種別推定の誤り率。
- 私設コーパスの文脈タグ付与の作業量見積り。
- カテゴリ分類の命名と粒度（`business` の扱い、`id-document` の細分化要否、
  カテゴリ名の英語表記が日本の利用者に伝わるか）。
- カテゴリ最適化（検出層スキップ）の同値性テスト戦略（対象は findings に
  限定済み・除外モードは 6.8 に明記済み。テストの具体設計が未着手）。
- `--only` 指定時の「他カテゴリとして検出された同一スパンが N 件ある」
  ヒント表示（6.8 の実測例: `--only birthdate` が保険者番号ラベル付き
  生年月日を 0 件と報告する、`--only custom` がカスタムルールの検出を
  重複解決の敗退で 1 件も出さない、のような沈黙を可視化する）。

## 11. 本設計で変えないもの

反証レビューで互換性が確認された、明示的に維持する契約:

- 終了コードの三値契約（0=なし / 1=検出 / 2=エラー）。
- baseline の fingerprint 形式（確信度を含まないため、確信度校正の
  影響を受けない）。
- ignore マーカー・allowlist の意味論。
- `[rules] disabled` による個別ルールの完全無効化。
