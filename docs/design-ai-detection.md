# Design Doc: ローカル推論モデルを主軸にした検出エンジンへの作り直し

- ステータス: ドラフト v1.1（独立した反証レビューは未実施。理由は §12）
- 作成日: 2026-10-07 / v1.1 改訂: 2026-10-07（§13 に PoC の結果を追記。本文中の【要確認】のうち PoC で決着したものは §13.5 にまとめ、本文は書き換えていない）
- 関連: [design-detect-report-enforce.md](design-detect-report-enforce.md)（報告層と強制層の再設計。本書は検出層だけを置き換え、同書の報告層と強制層の設計はそのまま活かす）

## 1. 要約

検出の起点を、ラベルやキーワード（以下、マーカー）から、ラップトップの CPU で動く日本語のトークン分類モデルへ移す。
モデルが「どこが PII らしいか」を文脈から判定し、検査用数字や郵便番号の実在照合のような決定的な検証器は、モデルが挙げた候補の確信度を上げ下げする確認役に回す。
ただしマイナンバーやクレジットカード番号のように検査用数字で真偽を決められる種別に限り、マーカーに依存しない構造照合を第二の起点として残す。
モデルは文字列の書式や検査用数字を学習で再現できず、文脈のない裸の番号を取りこぼすためである。

推奨する進め方は、既存の外部レコグナイザ連携（`internal/external`）を使った計測から始める段階移行である。
推論ランタイム（pure Go か ONNX Runtime か）と性能目標の達成可否は、その計測の結果で決める。
本書に出てくる性能値は、出典を付けた公開値か「未測定」のどちらかであり、手元で測った値はまだない。

## 2. 用語

- **PII**（Personally Identifiable Information、個人情報）：氏名、住所、電話番号、マイナンバーなど、個人を識別しうる情報。
- **マーカー**：本書では、現行ルールが検出の前提にしている周辺語を指す。`氏名:` のようなラベル、`様` のような敬称、`口座番号` のようなコンテキストキーワード、CSV のヘッダ列名がこれにあたる。
- **NER**（Named Entity Recognition、固有表現抽出）：文中の人名や地名などの区間を見つけて種別を付けるタスク。本書では、トークンごとに「PII の始まり、続き、PII 以外」のラベルを付けるトークン分類として実装するものを指す。
- **エンコーダモデル**：BERT 系の、入力全体を一度に読んで各トークンの表現を出すモデル。文章を生成しない。
- **ONNX**（Open Neural Network Exchange）：学習済みモデルの共通交換形式。ONNX Runtime（以下、ORT）はその推論エンジンで、C/C++ 製の共有ライブラリとして配布される。
- **INT8 量子化**：モデルの重みを 8 ビット整数に縮めて、サイズと CPU 推論時間を減らす手法。精度がわずかに落ちることがある。
- **GGUF**：llama.cpp 系の推論エンジンが読むモデル形式。主に生成型 LLM（Large Language Model、大規模言語モデル）で使われる。
- **確認器（confirmer）**：本書の新設語。モデルが挙げた候補に対して、検査用数字や辞書照合を当てて確信度を上げ下げする決定的な処理。現行の `Validate` 関数群と辞書（`internal/checksum`、`internal/dict`）を流用する。
- **コールドスタート**：プロセス起動からモデルとトークナイザを読み込み、最初の推論ができるまでの時間。

## 3. 背景と問題

### 3.1 現行エンジンは「マーカーがある PII」しか見ていない

現行の検出層（`internal/detect`、`internal/rule/builtin.go`）は、正規表現で値の書式を捉え、周辺のマーカーで確信度を決める構造になっている。
数字だけで真偽が決まらない種別（運転免許証、銀行口座、基礎年金番号など）は `RequireContext: true` で、マーカーがなければ報告しない。
氏名は、`氏名:` 系のラベル、担当や宛名のラベル、敬称、CSV と Markdown 表のヘッダ、名簿判定のいずれかを起点にしないと検出できない。
[detection-methods.md](detection-methods.md) の対応表も「氏名（完全なラベルなし）」を静的検出困難（×）としている。

この構造のため、精度改善はマーカー語彙の追加と例外処理の積み増しになってきた。
`NegativeContext` の語彙、採番ラベル隣接判定、隣接行昇格（40 ルーン窓）、CSV と Markdown 表の列文脈、クロスライン氏名、名簿判定は、どれもマーカーが届かない場面を個別に補う仕組みである。
[accuracy-roadmap.md](accuracy-roadmap.md) §3.2 も、40 ルーン窓を超えたラベルに昇格しない制約を「大規模な設計変更を伴う」将来課題として残している。

### 3.2 実測 F1 は、マーカーなしの PII に対する再現率を測っていない

README の実測 F1（medium プロファイルで 0.97 前後）は、非公開評価コーパス `private-eval-v2` に対する値である。
このコーパスの陽性ケースはルールごとに生成されており、`internal/corpusv2` の生成器はルールが検出できる形（ラベル付き、文脈語付き）を前提に作られている。
そのため「マーカーのない氏名や口座番号をどれだけ取りこぼすか」は、現在の数値に表れていない。
筆者の判断では、作り直しの成否はまずこの見えていない領域で測るべきであり、§8 で評価セットの作り直しを先に置いている。

### 3.3 ラップトップで動く日本語 PII モデルが出てきた

2026 年時点で、CPU だけで動く日本語特化の PII 抽出モデルが公開されている。
代表例の [Sumi](https://github.com/NagaYu/sumi) は、[ModernBERT-Ja-130M](https://huggingface.co/sbintuitions/modernbert-ja-130m)（MIT ライセンス、1.32 億パラメータ）をトークン分類に微調整したもので、氏名、住所、電話番号、マイナンバー、銀行口座、郵便番号など 10 種別を扱う。
Sumi の公開値は、ONNX INT8 の CPU 推論で 22.54 文書/秒、ピークメモリ約 1,000MB、テンプレートに依存しない評価で micro F1 0.953 である（文書長と計測機種は README から読み取れず【要確認】）。
ModernBERT-Ja のトークナイザは SentencePiece の unigram モデルで、MeCab のような日本語形態素解析器による前処理を要しない。
形態素解析器に依存しないことは、Go の単一バイナリへ組み込むうえで重要な条件になる。

## 4. 設計の目標と非目標

### 4.1 目標

- マーカーのない PII（ラベルなしの氏名、遠いラベルの口座番号、ヘッダのない表の住所）を検出できるようにする。
- 現行で検出できている PII の精度を落とさない。具体的な受け入れ条件は §9 に置く。
- 外部への通信なしで、一般的なラップトップの CPU だけで推論する。通信が発生するのはモデルの初回取得だけにする。
- pre-commit フック（staged diff の走査）で利用者が待てる時間に収める。目標値は §7 に仮説として置き、計測で確定させる。
- 利用者から見える契約（ルール ID、`.jp-pii.toml`、終了コード、JSON と SARIF の出力形式、`jp-pii-detector:ignore` マーカー、baseline）を維持する。

### 4.2 非目標

- 生成型 LLM による判定。理由は §5.3。
- GPU の利用や、クラウドの推論 API への送信。PII をリポジトリ外へ出さないことがこのツールの前提であるため。
- 常駐デーモンによるコールドスタートの回避。計測前に複雑さを足さない。§7 の計測で目標を外したときに改めて検討する。
- 報告層と強制層の再設計。[design-detect-report-enforce.md](design-detect-report-enforce.md) の範囲である。

## 5. 方式の選択

### 5.1 「ルールを全廃する」案を採らない理由

依頼の「ゼロベース」を「ルールを一切持たない純粋なモデル検出」と読むこともできる。
その案は、マーカーへの依存を消せる代わりに次の二つを失う。

一つは、文脈のない裸の番号の検出である。
Sumi 自身も、文脈のない 12 桁のマイナンバーは誤検出を抑えるため検出対象外にしている（同 README）。
現行の `jp-my-number` は検査用数字で 11 分の 1 まで偽陽性を絞れるので、文脈がなくても報告できる。
モデルにはこの剰余計算を学習で再現させられないので、この能力は構造照合でしか残せない。

もう一つは、書式の厳密さである。
`jp-postal-code` は実在する 7 桁の郵便番号の集合（ビットセット）と照合しており、`150-9999` のように前 3 桁が実在しても未割当の番号を棄却できる。
モデルは「郵便番号らしい並び」を見つけられても、割当の有無は知らない。

そのため本設計は、検出の起点（どこを候補にするか）をモデルに移し、真偽の判定に使える決定的な知識は確認器として残す。
ルールのうち捨てるのはマーカー語彙と、マーカーが届かない場面を補う仕組みであり、検査用数字と辞書は捨てない。

### 5.2 起点を二つ持つ

候補の起点は次の二つにする。

- **モデル起点**：トークン分類モデルが付けた PII 区間。すべての種別がこちらから出うる。氏名、住所、口座番号のように書式だけでは真偽が決まらない種別は、この起点からしか出ない。
- **構造起点**：検査用数字か実在照合で、文脈なしに真偽をほぼ確定できる種別だけに残す正規表現。対象はマイナンバー、クレジットカード番号、インボイス登録番号、メールアドレス（TLD 実在照合）、〒記号付きの郵便番号の 5 種別に限る。マーカー語彙は持たない。

二つの起点が同じ区間を挙げたときは、確信度の高いほうを残す（現行の `resolveOverlaps` と同じ方針）。

### 5.3 エンコーダのトークン分類を選び、生成型 LLM を選ばない

生成型の候補として、日本語 PII 抽出用の [LFM2-350M-PII-Extract-JP](https://docs.liquid.ai/lfm/models/lfm2-350m-pii-extract-jp.md)（GGUF 形式あり）がある。
このモデルは抽出結果を JSON の文字列リストで返し、位置を返さない。
同じ氏名がファイル内に複数回出ると、どの出現を指すのかが決まらず、行と列を報告する現在の出力契約を満たせない。
さらに生成型はトークンを一つずつ出力するので、同じ入力長ならエンコーダの一括推論より遅い（Sumi の README は 4B の生成型ローカル LLM 比で 162 倍速いと報告している）。
以上から、エンコーダのトークン分類を採る。

### 5.4 モデルの候補

第一候補は ModernBERT-Ja-130M を土台にしたトークン分類モデルである。
Sumi の重みをそのまま使うか、同じ土台から自前で微調整するかは、§8 の段階 0 の結果で決める。
Sumi の種別は 10 種で、本ツールのルール ID（20 前後）より粗い。
たとえば 12 桁の数字について、運転免許証、マイナンバー、住民票コードを区別しない。
自前で微調整する場合は、ラベル体系を本ツールのルール ID に合わせる（§6.4）。

Sumi の重みの再配布可否は【要確認】である。
コードは Apache-2.0、合成データは CC0-1.0 だが、Wikipedia 由来の学習データは CC BY-SA 4.0 であり、重みを本ツールのリリース資産として再配布してよいかを Hugging Face のモデルカードで確認する必要がある。

代替候補は [GLiNER2-PII](https://arxiv.org/pdf/2605.09973)（0.3B、Apache-2.0、42 種別）である。
日本語の性能は確認できていないため、ModernBERT-Ja 系が段階 0 の基準を満たさないときだけ評価する。

## 6. アーキテクチャ

### 6.1 パイプライン

```text
source ──▶ segment ──▶ model（モデル起点）──┐
   │                                        ├─▶ confirm ──▶ calibrate ──▶ filter ──▶ report
   └────▶ normalize ──▶ structural（構造起点）┘
```

| 段 | 責務 | 現行コードとの関係 |
|---|---|---|
| source | 走査対象の列挙、文字コードの判定と変換、diff の取得 | `internal/source` をそのまま使う |
| segment | ファイルをモデルの入力長に収まる行単位の窓に分け、トークン位置と元テキストの行列位置の対応表を持つ | 新設 |
| model | 窓ごとにトークン分類を行い、区間、種別、スコアを出す | 新設（`internal/model`） |
| normalize | 全角英数字とハイフン類の 1:1 正規化 | `internal/normalize` をそのまま使う。構造起点と確認器だけが使い、モデル入力には原文を渡す |
| structural | §5.2 の 5 種別だけの構造照合 | `internal/rule` から該当パターンだけを残す |
| confirm | 検査用数字、郵便番号ビットセット、市区町村辞書、姓名辞書、TLD で確信度を上げ下げする | `internal/checksum` と `internal/dict` を流用する |
| calibrate | モデルスコアと確認結果を low、medium、high の 3 段階へ写像する | 新設 |
| filter | allowlist、`jp-pii-detector:ignore`、diff の追加行判定、baseline | 現行の処理を移す |
| report | text、JSON、SARIF、GitHub 形式で出力する | `internal/report` をそのまま使う |

source と report を作り直さない理由は、この二つがマーカーに依存していないからである。
文字コード判定（ISO-2022-JP、BOM なし UTF-16、Shift_JIS など）や JSON の `\u` エスケープ復号は、モデルに渡す前の原文を正しく得るために引き続き必要になる。

### 6.2 消すもの

次の仕組みは、モデルが文脈を読むことで不要になるため削除する。

- コンテキストキーワードと `NegativeContext` の語彙、採番ラベル隣接判定
- 隣接行昇格（40 ルーン窓）とクロスライン氏名
- CSV と Markdown 表の列文脈（ヘッダ行も窓の中に入れてモデルに読ませる。ヘッダから遠い行の扱いは §6.3）
- 名簿判定（`person-name-roster`）と高再現率ルール群（`--high-recall` の役割は §6.6 の閾値に置き換える）
- 構造起点に残さない種別の正規表現（運転免許証、銀行口座、氏名、住所、生年月日など）

### 6.3 窓の切り方と位置の対応

ModernBERT-Ja の最大入力長は 8,192 トークンだが、ファイル全体を一度に入れると注意機構の計算量が入力長の 2 乗で増える。
そこで行単位で 512 トークン前後の窓に切り、前後の窓と数行ずつ重ねる（窓長と重ね幅は段階 0 で決める）。
重なり部分で同じ区間が二度出たら、スコアの高いほうを残す。

CSV と TSV は、各窓の先頭にヘッダ行を付け加えてからモデルに渡す。
現行の列文脈がヘッダから遠い行にも列名を届けているのと同じ効果を、モデル入力の側で得るためである。
付け加えたヘッダ行の上で出た区間は報告しない。

位置は、トークナイザが返す各トークンの元テキスト上の文字オフセットから、行番号とルーン単位の列に戻す。
この座標系は外部レコグナイザのプロトコル v1（`internal/external`）が定めた、1 始まりの行とルーン単位の列、長さと同じものにする。

### 6.4 種別とルール ID の対応

モデルのラベルはルール ID に一対一で合わせる。
ルール ID は [roadmap.md](roadmap.md) が v1.0 の後方互換対象に挙げており、`.jp-pii.toml` の `[rules] disabled`、allowlist、baseline の fingerprint（ルール ID、ファイル、検出値から計算する HMAC）がこれに依存しているからである。

Sumi の重みをそのまま使う段階では、Sumi の 10 種別を既存のルール ID に写像し、写像できない種別（`JP_MEMBER_ID`、`DATE_TIME` の一部）は報告しない。
12 桁の数字のように Sumi が区別しない種別は、構造起点（マイナンバー）に該当しなければ報告しない。
運転免許証や住民票コードの区別は、自前で微調整したモデルに持たせる。

### 6.5 確認器の働き

確認器は候補を作らず、確信度だけを動かす。

- 構造起点の 5 種別は、検証に通れば high、通らなければ棄却する（現行と同じ）。
- モデルが電話番号と判定した区間は、市外局番辞書（`area_codes.txt`）と桁数の検証に通れば確信度を上げる。通らなければ low に落とす。
- モデルが住所と判定した区間は、番地相当の数字を含まなければ low に落とす。市区町村辞書に一致すれば確信度を上げる。
- モデルが氏名と判定した区間は、姓名辞書に一致すれば確信度を上げる。一致しなくても棄却はしない。辞書にない氏名を拾えることが、モデルを入れる目的の一つだからである。

住所に番地を要求する理由は §11 の 1 つ目のシナリオにある。
地名だけの区間を住所として報告すると、町字辞書のような地名の一覧ファイルで大量の誤検出が出る。

### 6.6 確信度の校正とプロファイル

モデルのスコアは確率として校正されていないので、評価セットの検証用分割でスコアと実際の適合率の対応を測り、区間ごとに low、medium、high の閾値を決める。
閾値はルール ID ごとに持ち、モデルの重みと一緒に配布する。

`--high-recall` は「低い閾値を使う」という意味に置き換える。
既存の `min_confidence` と `--fail-on`（design-detect-report-enforce.md の設計）はそのまま使える。

### 6.7 diff 走査

「検出値が追加行にある検出だけを報告する」という現行の規則は維持する。
窓にはハンクの文脈行（`git diff -U3` の前後 3 行）も含めてモデルに読ませ、追加行に区間が乗った検出だけを残す。
現行には「文脈行は確信度を上げるだけで、抑制には使わない」という規則があるが、モデルは抑制の概念を持たないので、この規則に相当する処理はなくなる。
ただし文脈行の内容でモデルのスコアが下がることはありうる。
その結果として新しく追加した PII を見逃す頻度は、段階 0 の評価セットで別に測る。

### 6.8 モデルの配布

モデルの重みは数百 MB 規模になるため、バイナリには埋め込まない（INT8 の ONNX で 130〜140MB 程度と推定。類似規模の [PiiScan](https://huggingface.co/vectorsense/piiscan) がトークナイザ込みで約 139MB）。

- 重みは GitHub Release の資産として配布し、バイナリにはファイルの SHA-256 を固定で埋め込む。取得後に照合し、一致しなければ使わない。
- 初回実行時に `os.UserCacheDir()` 配下へ取得する。明示的に取得する `jp-pii-detect model fetch` も用意する。
- CI とオフライン環境のために、モデルの置き場所を環境変数で指定でき、Docker イメージ（`ghcr.io/baneido/jp-pii-detector`）には重みを同梱する。
- モデルが取得できないときは、構造起点だけで走査を続け、モデル起点が無効だったことを標準エラーと終了コード 2 で知らせる。黙って精度を落とした走査を成功扱いにしない。

外部と通信するのは重みの取得だけで、推論に PII を外へ送ることはない。

## 7. 推論ランタイムと性能

### 7.1 ランタイムの候補

| 案 | 内容 | 捨てる理由になりうる欠点 |
|---|---|---|
| (a) pure Go | [hugot](https://pkg.go.dev/github.com/knights-analytics/hugot) の Go バックエンド。cgo 不要で、現行の 6 ターゲットのクロスコンパイルを保てる | hugot 自身が「性能要件があるなら C バックエンドへ移れ」と書いている。SentencePiece unigram（語彙 102,400、byte fallback 付き）のトークナイザに対応しているかは【要確認】で、未対応ならこの案は成り立たない |
| (b) ORT | hugot の ORT バックエンドか onnxruntime の Go バインディング。CPU 推論が最も速い | cgo と、プラットフォームごとの `libonnxruntime` 共有ライブラリが要る。リリース資産を 6 ターゲット分作り直し、Windows と macOS のライブラリ配置を扱う必要がある |
| (c) 外部プロセス | 既存の `internal/external`（JSONL で子プロセスとやりとりする）に、Python と ORT で書いた推論スクリプトをつなぐ | 利用者に Python 環境を要求するので、既定の配布形態にはできない |

推奨は、(c) で段階 0 の計測を行い、その結果で (a) と (b) を決める進め方である。
(c) は既に実装済みで、Go 側に推論コードを書く前にモデルの精度を非公開コーパスで測れる。
(a) と (b) の選択は、トークナイザの対応と、(a) の速度が §7.2 の目標に収まるかで決まる。

### 7.2 性能の目標（仮説）

pre-commit で効くのはスループットよりコールドスタートである。
staged diff の入力は数ハンク程度なので、推論そのものより、毎回のプロセス起動で 130MB 級の重みと 10 万語彙のトークナイザを読み込む時間が支配的になると推測する。
Sumi の 22.54 文書/秒はスループットの値で、コールドスタートについては何も言っていない。

本書が置く目標は次のとおりで、いずれも未測定の仮説である。

- staged diff（数ハンク）の走査を、Apple Silicon の M1 相当で 1.5 秒以内、AVX2 世代の x86 ノートで 3 秒以内に終える。
- このリポジトリ全体のフルスキャンを、CI ランナーで 10 分以内に終える。

### 7.3 メモリの扱い

現行は `GOMEMLIMIT=128MiB` で RSS を約 125MB に抑えられ、[integrations.md](integrations.md) もこれを前提に運用指針を書いている。
Sumi の公開値ではピークメモリが約 1,000MB であり、モデルを使う走査ではこの指針が成り立たない。
新しいメモリの目安は段階 0 で測り、integrations.md を書き直す。
フルスキャンの並列度は、モデルのセッションを 1 つ共有して窓をバッチで流す形にし、ワーカーごとにモデルを複製しない。

## 8. 移行計画

### 段階 0：計測（Go 側の推論コードは書かない）

1. 評価セットを作り直す。現行の `private-eval-v2` に加えて、マーカーのない PII を集めた区分を新設する。ラベルなしの氏名、40 ルーンより遠いラベルの口座番号、ヘッダのない表、自由文中の住所などである。生成器はモデルの学習データと別系統にし、手で集めた実例も混ぜる（同じ生成器で作ったデータで学習と評価を行うと、評価値が実力より高く出るため）。
2. Sumi の ONNX INT8 を `internal/external` 経由でつなぎ、既存区分と新区分の両方で精度を測る。評価基盤（`internal/eval`）から外部レコグナイザを通す経路が既にあるかは【要確認】で、なければ評価用に足す。
3. M1 相当の Mac と AVX2 世代の x86 ノートで、コールドスタート、窓あたりの推論時間、ピークメモリを測る。
4. hugot の Go バックエンドで ModernBERT-Ja のトークナイザが動くかを確かめ、動けば (a) の速度も測る。

段階 0 の出口で、§9 の基準に照らして続行するかを決める。

### 段階 1：二つのエンジンを並走させる

`--engine=model` を opt-in で追加し、既定は現行エンジンのままにする。
`internal/model`、segment、calibrate を実装し、評価基盤は両エンジンの値を並べて出す。

2026-10-08 時点の実装状況は次のとおりである（段階 0 の計測はメンテナの判断で省略した）。

- フラグは `--engine=model` ではなく `--model-dir <dir>` にした。指定すると、組み込みルールの検出にモデル起点の検出を加える（§13.2 の併用構成）。
- 推論は ORT の公式 Go バインディング（`github.com/microsoft/onnxruntime/go`）で行う。cgo が必要なので `-tags ort` のビルドにだけ組み込み、配布バイナリ（`CGO_ENABLED=0`）は従来どおりになる。hugot は Go 1.27 と大きな依存ツリーを要求するため使わなかった。
- トークナイザは Unigram の最小実装を Go で書いた（`internal/model/tokenizer.go`）。このリポジトリの 154 ファイル（約 78 万トークン）で、Hugging Face tokenizers と ID と文字オフセットが一致することを確かめた。
- 確認器（§6.5）は組み込みルールの正規表現と検証関数を再利用する。数字列はモデルの種別を使わず、書式から種別を付け直す（§13.3）。
- モデルの候補は外部レコグナイザと同じ検証（無効化ルール、ignore マーカー、allowlist、min_confidence）と、組み込みルールと同じパス降格と重複解決を通る。diff 走査では、追加行に乗る候補だけを残す。
- §13.2 の評価セット 59 件で、マーカーなし区分の再現率 0.97、誤検出 0 件となり、PoC の併用構成と同じ結果になった。

先送りした項目は次のとおりである。

- 窓の重ね合わせ（§6.3）。窓の境界をまたぐ PII は分断される。
- 確信度の閾値の校正（§6.6）。PoC の値（0.5、0.7、0.95）をそのまま使っている。たとえば都道府県のない住所は、文脈しだいで確率が 0.5 前後になり、報告されないことがある。
- 評価基盤（`internal/eval`）での両エンジンの並列表示。
- モデルの初回取得と SHA-256 による固定（§6.8）、ORT 共有ライブラリの配布。現状は利用者がモデルと ORT を用意する。
- CSV と TSV の窓へのヘッダ行の付加（§6.3）。
- モデル由来の検出への下位種別（`Reason.Kind`）の付与。現状はモデルが検出した電話番号に種別が付かないので、`[rules] exclude_kinds` が効かない。
- 大きなファイルでのメモリ。トークナイザは 1 ファイルを丸ごと分割するので、5MB の数字主体のファイルでは、1 ワーカーあたり数百 MB の一時メモリを使うと見積もっている（未測定）。`GOMEMLIMIT=128MiB` の運用指針（integrations.md）は、`--model-dir` 使用時には成り立たない。

### 段階 2：自前のモデルを学習する

ModernBERT-Ja-130M から、本ツールのルール ID をラベルにしたトークン分類モデルを微調整する。
学習データは、既存の合成生成器（`internal/fixturegen`、`internal/corpusv2`）を、コード、設定、CSV、JSON、ログ、自由文といった多様な文脈へ値を埋め込む形に広げて作る。
難しい負例として、このリポジトリの辞書ファイルや、公開 OSS のテストデータにある番号風の文字列を入れる。

### 段階 3：既定を切り替え、マーカー機構を消す

§9 の基準を満たしたら既定エンジンをモデルに切り替え、§6.2 の仕組みを削除する。
検出結果が変わる変更なので、[roadmap.md](roadmap.md) の方針どおりマイナーバージョンで出し、リリースノートに明記する。

## 9. 切り替えの判定基準

次の 3 つをすべて満たしたら段階 3 へ進む。数値は本書が置く提案で、段階 0 の結果を見て見直す。

- 既存区分の medium プロファイルで、行レベル micro F1 が現行値から 0.01 以上下がらない。
- マーカーなし区分の再現率が 0.80 以上（現行エンジンの同区分の値も段階 0 で測り、併記する）。
- §7.2 の staged diff の時間目標を、両方の機種で満たす。時間は OS のファイルキャッシュが冷えた状態（再起動直後の最初の走査に相当）で測る。M5 Max の冷えた状態で測った 1.74 秒（§13.4）は許容範囲とする（2026-10-07 にメンテナが判断）。

## 10. CI ゲートと互換性への影響

**精度ゲート**：現行の `docs/accuracy.json` はルールごとの数値を完全一致で照合している。
INT8 推論は CPU の命令セットによって結果がわずかに変わりうるうえ、GitHub のホストランナーはジョブごとに CPU の型番が変わりうる。
そこで完全一致をやめ、プロファイル単位の F1 に許容幅（提案は ±0.005）を設けたゲートに変える。
README の数値は CI ランナーで測った値から生成する。

**データセット品質ゲート**：全ルール ID に陽性 10 件以上を求める現行の条件は維持する。
加えて、マーカーなし区分が全体の一定割合以上を占めることを条件にする（割合は段階 0 で決める）。

**ドッグフーディング**：このリポジトリには姓名辞書や町字辞書のような、PII に似た一覧ファイルがある。
町字辞書（`internal/dict/towns.txt`）は現在 allowlist の除外対象ではない。
モデルエンジンでは辞書ファイル群を allowlist に入れることになる見込みで、それで検出 0 件を保てるかは段階 1 で確かめる。

**baseline**：fingerprint は検出値の文字列を含むので、モデルの更新で区間の境界が 1 文字でもずれると、既存の baseline に載っていた検出が新規扱いで再報告される。
モデルの重みを更新するリリースでは、リリースノートで baseline の再作成を案内する。

**出力契約**：終了コード、JSON と SARIF の形式、ルール ID、`jp-pii-detector:ignore` は変えない。
JSON の各検出に、どちらの起点から出たかを示すフィールドを足す（フィールドの追加は互換の範囲）。

## 11. 壊れるシナリオ

本書の設計が破綻しうる具体的なシナリオと、その対処を挙げる。

1. **地名の一覧で LOCATION が大量に出る。**
   町字辞書は 95,007 行の地名の一覧である。
   モデルが地名に LOCATION を付けると、ほぼ全行が住所候補になる。
   現行の `jp-address` は番地を必須にしているのでこの問題が起きていない。
   対処として、確認器で番地のない住所区間を low に落とし（§6.5）、既定の min_confidence では報告しない。

2. **x86 ノートでコールドスタートが目標を大きく超える。**
   pre-commit フックが遅いと、利用者はフックを外す。
   対処は段階 0 の計測であり、目標を外したら §9 の基準により既定を切り替えない。
   常駐デーモンは計測結果を見てから検討する（§4.2）。

3. **pure Go でトークナイザが動かない。**
   (a) 案が成り立たず、(b) の ORT と共有ライブラリの配布が必須になる。
   リリース手順（`release.yml`）の作り直しが段階 1 の作業に加わる。

4. **文脈のない番号をモデルが拾わない。**
   たとえば検査用数字が正しい 12 桁が、文脈なしで JSON の値に入っている場合である。
   この場合は構造起点（§5.2）で拾う。
   拾えないのは、構造起点に残さない種別（運転免許証、銀行口座など）の、文脈のない値である。
   これは現行エンジンでも検出していない（`RequireContext`）ので、退行にはならない。

5. **モデル更新で検出結果がリリースごとに揺れる。**
   ルールの変更と違い、重みの更新はどの検出が変わるかを差分で読めない。
   対処として、モデルの重みはバイナリのバージョンに SHA-256 で固定し、勝手に更新しない。
   重みを変えるリリースでは、評価セット上で増減した検出をリリースノートに載せる。

## 13. PoC の結果（2026-10-07）

§8 の段階 0 の 4 項目を小規模に実施した。
評価セットは手書きの小規模版で代用し、非公開評価コーパス（`private-eval-v2`）での計測は行っていない（このセッションでは `$JP_PII_FIXTURES` が未設定だったため）。
計測機は Apple M5 Max（18 コア、メモリ 128GB）で、§7.2 が想定する一般的なラップトップより大幅に速い。
以下の時間はすべてこの機種での値であり、M1 相当や x86 ノートでは未測定である。
PoC のスクリプトと評価セットはリポジトリに入れていない。

### 13.1 構成

Sumi の ONNX INT8 版（`NagaYu/sumi-ja-pii` の `model.int8.onnx`、133MB）を、Sumi 側のルール層と境界補正を使わずにモデル単体で動かした。
モデル出力に、§6.5 の確認器の最小版を Python で後付けした。
確認器の内容は、番地のない住所を落とす、`@` を含まないメールアドレスを落とす、番号系の種別に桁数と検査用数字の検証を当てる、の 3 つである。

### 13.2 精度：マーカーなしの PII で再現率が大きく上がった

評価セットは筆者が手で書いた 59 件（マーカーあり 15 件、マーカーなし 25 件、PII を含まない紛らわしい負例 19 件）で、正解区間はマーカーあり 19 区間、マーカーなし 40 区間である。
一致は区間の重なりで判定し、種別の一致は問わない。

| 条件 | マーカーあり再現率 | マーカーなし再現率 | 誤検出区間 | 誤検出が出た負例 |
|---|--:|--:|--:|--:|
| 現行エンジン（既定） | 16/19（0.84） | 16/40（0.40） | 0 | 0/19 |
| 現行エンジン（`--high-recall --name-roster`） | 17/19（0.89） | 18/40（0.45） | 1 | 1/19 |
| Sumi 単体 | 19/19（1.00） | 36/40（0.90） | 7 | 3/19 |
| Sumi と確認器 | 19/19（1.00） | 34/40（0.85） | 0 | 0/19 |
| 現行エンジンと「Sumi と確認器」の併用 | 19/19（1.00） | 39/40（0.97） | 0 | 0/19 |

現行エンジンがマーカーなし区分で落とした 24 区間のうち 21 区間は氏名で（自由文、ログ、コードの引数、ヘッダのない CSV、箇条書きの名簿）、残り 3 区間は都道府県のない住所やラベルのない住所だった。
Sumi はそのほとんどを拾った。

Sumi と確認器の構成が落とした 6 区間の内訳は次のとおりである。
- 文脈のない裸のマイナンバー 2 件。Sumi 単体の段階で拾えておらず、現行エンジンは検査用数字で拾っている。この 2 件は §5.2 で構造照合を第二の起点として残した判断を支持する。
- カード番号 1 件と国際表記の電話番号 1 件。Sumi 単体は拾っていたが、確認器の書式検証で落ちた（原因は §13.3 の種別の取り違え）。
- フリーダイヤル 1 件とローマ字の氏名 1 件。Sumi 単体の段階で拾えていない。

併用の構成が 0.97 になるのは、上の 6 区間のうちローマ字の氏名以外の 5 区間を現行エンジンが補うためである。

この表には二つの偏りがある。
一つは、評価セットを筆者一人が書き、しかも確認器の条件をこのセットの誤検出を見て決めたことである。
もう一つは、件数が少なく、1 区間で再現率が 2.5pt 動くことである。
したがってこの表から言えるのは「マーカーなしの氏名で差が大きい」という方向までで、F1 の水準は §8 の評価セットで測り直す必要がある。

### 13.3 誤検出：コードを読むとメールアドレスの誤検出が大量に出る

独立した負例として、このリポジトリ全体（allowlist は現行の `.jp-pii.toml` を適用）を `internal/external` 経由で Sumi に走査させた。
Sumi 単体の検出は 4,251 件で、内訳はメールアドレス 3,012 件、氏名 938 件、住所 102 件ほかだった。

- メールアドレスの 3,012 件は、コード中の `_mail` や `user` のような識別子である。Sumi は自由文で学習しているので、コードは学習分布の外にある。§8 段階 2 の学習データにコード、設定、ログを入れる必要がある。
- 住所の 102 件のうち 64 件は町字辞書（`internal/dict/towns.txt`）の地名で、番地を要求する確認器ですべて落ちた。§11 のシナリオ 1 は実際に起き、§6.5 の対処で防げた。
- 確認器を通ったあとの検出は、辞書ファイルとテストとフィクスチャ以外では 11 件だった。内訳は、コメントやドキュメント用文字列に例として書かれた氏名 10 件と、例示のメールアドレス 1 件である。残りの約 990 件は、辞書ファイル（大半が姓名辞書）とテストとフィクスチャに出た。モデルエンジンでドッグフーディングの検出 0 件を保つには、姓名辞書の allowlist 追加と、テスト中の例示氏名への ignore マーカー付与が要る。

もう一つの知見は、Sumi が数字列に付ける種別が当てにならないことである。
カード番号や国際表記の電話番号に別の種別を付けたり、区間の境界をずらしたりしたため、種別ごとの書式検証を当てると正しい検出まで落ちた（§13.2 で再現率が 0.90 から 0.85 に下がった原因）。
本実装では、数字を主とする区間は Sumi の種別を使わず、書式から種別を付け直す。

配布形態に近い Go と ORT の経路で見ると、OS のファイルキャッシュが温まっていれば 0.33 秒で、§7.2 の目標（M1 相当で 1.5 秒）に収まった。
一方、キャッシュが冷えた初回は 1.74 秒で、この M5 Max でも目標を超えた。
再起動直後の最初のコミットではこの程度かかり、一般的なラップトップではさらに遅くなると推測する。
§9 の時間基準は冷えた状態で判定することにし、この 1.74 秒は許容範囲と判断した。
Python の経路の 0.45〜0.60 秒は、配布形態と異なるので参考値にとどめる。
フルスキャンは、現行エンジンより桁違いに遅い。
CI での全量走査は、追加行だけを走査する diff モードを基本にし、全量走査は定期実行に回す必要がある。

ランタイムの選択肢（§7.1）は次のように決着した。

- **(a) pure Go**：hugot v0.8.2 の Go 側トークナイザは Unigram に対応していた。しかしモデルのグラフ変換（onnx-gomlx）が `BroadcastToShape: rank mismatch` で失敗した。fp32 版でも同じエラーが出たので、原因は量子化ではなく、ModernBERT のグラフに含まれる演算の扱いと判断する。現時点ではこの案は使えない。
- **(b) ORT**：Go から動作した。cgo と、プラットフォームごとの `libonnxruntime` 共有ライブラリが必要になる。hugot は Go 1.27 を要求するので、本リポジトリ（Go 1.26.1）の Go を上げる必要もある。hugot が返す位置はバイト単位なので、ルーン単位の列への変換を実装する必要がある。
- **(c) 外部プロセス**：§13.3 のリポジトリ全体の走査はこの経路で行い、既存のプロトコル v1 のまま動いた（§13.2 の精度表は、`--stdin` と Python から直接比較した）。

以上から、現時点の推奨は (b) である。
(a) の失敗は onnx-gomlx 側の不具合とみられ、設計上不可能なわけではない。onnx-gomlx が修正されたら再評価する。
残る作業は、6 ターゲットそれぞれの ORT 共有ライブラリを配布する方法の設計である。
バイナリと同じアーカイブに同梱するか、モデルと同じく初回に取得するかを決める必要がある。
